# コーディング規約・実装方針

## 1. 命名規則

### 1-1. データベース（MySQL）命名規則

| 項目 | 命名規則 | 例 | 備考 |
|---|---|---|---|
| テーブル名 | snake_case（複数形） | `works`, `blog_posts` | Laravel Eloquentに準拠 |
| カラム名 | snake_case | `work_id`, `published_at` | `created_at`・`updated_at` は自動管理カラム |

### 1-2. PHP（Laravel）命名規則

**モデル・テーブル関連**

| 項目 | 命名規則 | 例 | 備考 |
|---|---|---|---|
| モデル名（クラス名） | PascalCase（単数形） | `Work`, `BlogPost` | Eloquentモデル |
| テーブル名 | snake_case（複数形） | `works`, `blog_posts` | モデルと対応。自動で解決される |

**プロパティ・メソッド・変数名**

| 項目 | 命名規則 | 例 | 備考 |
|---|---|---|---|
| プロパティ名（モデルの属性） | snake_case | `published_at`, `is_published` | DBカラムと対応 |
| メソッド名 | camelCase | `labelText()`, `bodyHtml()` | Laravel・PSRに準拠 |
| 変数名 | camelCase | `$latestPosts`, `$totalPrice` | PHP全体の標準 |
| 定数名 | SNAKE_CASE（全大文字） | `LABELS`, `DEFAULT_LIMIT` | |

**URL / ルート / Bladeファイル命名規則**

ルート名、URLパス、Bladeファイル名は、以下のように命名する。

| 項目 | 命名規則 | 例 | 備考 |
|---|---|---|---|
| ルートURL | kebab-case（小文字＋ハイフン） | `/works/{work}`, `/blog` | SEO・可読性の観点 |
| ルート名（name） | dot区切りのスネークケース | `posts.index`, `inquiries.store` | Laravel標準の命名パターン |
| Bladeファイル名 | snake_case（小文字＋アンダースコア） | `index.blade.php`, `inquiry_received.blade.php` | URLやルート名と対応を意識する |
| Bladeファイルのディレクトリ構造 | リソースごとにディレクトリ分け | `posts/index.blade.php`, `works/show.blade.php` | スケーラビリティ重視 |
| コンポーネントBlade | kebab-case | `<x-work-card>` | HTMLのタグ名として使うため、小文字＋ハイフン |

### 1-3. JavaScript命名規則

| 要素 | 命名規則 | 例 | 備考 |
|---|---|---|---|
| 変数・関数名 | camelCase | `userName`, `fetchData` | JS標準に準拠 |
| 定数 | SNAKE_CASE（全大文字） | `MAX_RETRY`, `API_ENDPOINT` | 再代入しない値 |
| ファイル名（ユーティリティ） | camelCase.js | `formatDate.js` | |

### 1-4. その他

ここまでに言及されなかった点で悩んだ場合は、できる限り [PER Coding Style](https://www.php-fig.org/per/coding-style/)（PSR-12の後継）に準拠する。整形は Laravel Pint に任せる。

## 2. 実装方針

### 2-1. URL設計

- RESTfulなURL設計にする（Laravel公式ドキュメントのリソースコントローラーの例を参考にする）
- URL内にモデルのキーが自然に含まれるので、**ルートモデル結合を活用する**。公開ページのURLにはIDではなく `slug` を使う（`getRouteKeyName()` で指定）
- 型にはまらないものは柔軟に対応する（例：`GET /works/csv-download`）

### 2-2. 定数

いくつかのレベルに分けて管理する場所を決める。

**あるモデル（テーブル）単体に関連するもの**
- モデルファイル `App\Models\Hoge.php` の中に定義する
- 実績のラベル（サンプル／提案デモ／制作実績）のような、DBでは管理していないコードがこれに該当する

**システム全体で扱うもの**
- `config/const.php` の中に定義する
- 必要がなければ無理に作る必要はない
- ページネーションの1ページの表示数などが該当する

**環境変数から取得するもの**
- `.env` やサーバーの環境変数で管理している値を参照するために定義する
- 役割ごとに分けて `config` 配下にファイルを作成する（例：サイトの表示情報・通知先は `config/site.php`）

切り分けるのが難しい汎用的な値は、「システム全体で扱うもの」に含めてかまわない。

### 2-3. 共通化

**ユースケース**
- 使いまわせる処理を `app/UseCases` 配下に作成する。対象のモデルや機能で自由にフォルダを作ってかまわない
- 基本的に1クラス1アクションとする。プライベートメソッドの数に制限はない
- 引数に `Request` オブジェクトを渡すことはできる限りやめる（同じ処理をバッチやジョブ、Filamentの管理画面から行うときに使えなくなるため）
- Eloquentをユースケース内で扱うのは問題ない
- Controllerのアクションが肥大化してきた場合の切り出し先として使ってもかまわない

**FormRequestとUseCaseの責務分担**
- バリデーション（項目単位のルール、および相関チェック）はFormRequestに集約する（`withValidator`・カスタムルールを含む）
- UseCaseは、保存処理・副作用（セッション処理、メール送信等）・業務ロジックに専念する

**サービス**
- 下準備をしてから処理を実行しなければならない、1セッション内で状態を保持する必要がある場合に、その機能をまとめる先として `app/Services` 配下に作成する
- 大きめの機能をまとめるために使うので、基本的にはユースケースに書けばよい
- 実際に使う場合にはファサードを定義し、そちらを呼ぶことが多い
- サービス化の目安：外部APIとの送受信、決済処理、SMS送信など

**トレイト**
- `app/Traits` 配下に作成する
- モデルに機能を持たせる場合に作成するのが主な使い方だが、あまり使わない

### 2-4. ルートファイルの分割

- ルート定義は、アクターごとに `routes/{アクター識別子}.php` として分割する
  - toshLabでは、訪問者向けの公開ページを `routes/public.php` にまとめる
  - 管理画面はFilamentのパネル（`app/Providers/Filament/AdminPanelProvider.php`）がルートを持つため、ルートファイルは作らない
- 特定のアクターに属さない横断的機能は、機能名でファイルを分ける（例：`routes/auth.php`）
- 各ファイルには、そのアクター（または横断的機能）に関する全リソースのルートをまとめて記述する。リソースごとにファイルを分けることはしない
- `routes/web.php` は、各ルートファイルを `require` するだけの構成とする

### 2-5. メッセージの管理

- ユーザーに表示するメッセージ（バリデーションメッセージ、完了メッセージ等）は、実装側にハードコードせず `lang/ja/` 配下の言語ファイルに定義する
- 実装側・テスト側の両方で、同じ言語ファイルのキー（例：`__('inquiry.sent.title')`）を参照する。メッセージの文字列そのものを、実装・テストにそれぞれ直接書かない（二重管理を避け、変更時の修正漏れ・食い違いを防ぐため）
- 新しいメッセージを追加する場合は、対応する機能の言語ファイル（無ければ新規作成）にキーを追加してから、実装・テストの両方でそのキーを参照する
- ページ本文の固定の文章（キャッチコピー、サービス説明など）は、言語ファイルではなくBladeに直接書いてよい（翻訳の予定がなく、デザインと一緒に読めるほうが直しやすいため）

### 2-6. コメントの付け方

- 実装コード（Controller・UseCase・Model等）には、後からコードを読む人が理解できるよう、最低限のコメントを付与する
- コメントを付けるべき箇所は、**「なぜこの実装・この条件になっているのか」がコード単体では読み取りにくい部分**に絞る（例：一見遠回りに見えるが意図があるロジック、スパム対策、セキュリティ上の理由がある処理）
- 単純な処理（値の代入、シンプルなgetter/setter等）には、自明なため付けない
- テストコードにも同じ考え方を適用する

### 2-7. 日付の扱い

- 年月（`YYYYMM`）の文字列は `Carbon::createFromFormat('!Ym', …)` で解釈する。`!` を付けないと、指定していない日・時刻が「今日」で補われる。そのため、今日が31日のときに `202602` を解釈すると「2月31日」となり、3月3日に繰り上がる
- 月の加減算は `subMonthNoOverflow()`／`addMonthNoOverflow()` を使う。`subMonth()`／`addMonth()` は月末で狙った月にならない（例：3月31日の `subMonth()` は2月ではなく3月3日になる）
- 日付に依存するテスト（ブログの予約投稿など）は、`travelTo` で時刻を固定する

### 補足：FormRequestでの任意項目（nullable）の取り出し方

- `$request->validated()`（引数無し）が返す配列は、**リクエストに存在しなかったキーを含まない**（`nullable` ルールを付けていても同様）。そのため `$validated['foo']` のような直接の配列アクセスは、その項目が未送信のときに「Undefined array key」の警告となり、Laravelの既定のエラーハンドラによって例外に昇格し500エラーになる
- 任意項目を取り出す場合は、`$request->validated('foo')`（キー指定。存在しなければ `null` を返す）か `Arr::get($validated, 'foo')` を使う。`$validated['foo'] ?? null` という書き方も、`??` の左辺で配列アクセスした時点で警告が発生するため不十分な対策である点に注意

## 3. 公開リポジトリとしての注意

このリポジトリはポートフォリオとしてGitHubで公開する。

- 実名・勤務先・本業のクライアント名・個人のメールアドレスを、コード・コメント・コミットメッセージ・ドキュメントに書かない。表示名は `config/site.php` の `owner` を使う
- 秘密情報（パスワード、APIキー、通知先メールアドレス）は `.env` にだけ書く。`.env.example` にはダミー値かキー名だけを書く
